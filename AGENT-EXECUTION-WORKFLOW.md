# Методика работы с ИИ-агентами: исследование → доказательства → Draft PR → независимая приёмка

**Решение владельца: 03.11.2026.** Общая операционная методика для всех репозиториев saymer-alt и разных исполнителей: Z AI / ZCode, Kimi Code, Codex, Cursor и иных агентов. Не требует определённой модели, подписки, IDE или сервиса.

**Статус:** документирует практику организации заданий и передачи результатов. Не заменяет [AGENT-TASK-CONTRACT.md](AGENT-TASK-CONTRACT.md), [AGENT-ENGINEERING-STANDARD.md](AGENT-ENGINEERING-STANDARD.md), [PROOF-BEFORE-BUILD.md](PROOF-BEFORE-BUILD.md), местные AGENTS.md, конституции проектов, CI и owner GO. При конфликте применяется более строгий safety-контракт.

## 1. Цель и главное отличие

Оптимизировать **полезные проверенные результаты**, а не число коммитов, PR, токенов, пройденных шагов или длину отчёта. Агент может быстро написать код, но это не означает, что код безопасен и готов к слиянию.

Рабочий цикл:

~~~text
Постановщик: актуальный GitHub + контракты + цель + безопасные границы
                           ↓
Агент: инвентаризация и проверка «не сделано ли уже»
                           ↓
      минимальное воспроизведение / независимая гипотеза
                           ↓
          узкое исправление + негативный тест
                           ↓
       изолированные тесты → Draft PR (если нужен)
                           ↓
    перепроверка CI и конфликтов на ИТОГОВОМ head SHA
                           ↓
Независимое ревью: контрпример, blast radius, доказательства
                           ↓
      владелец: GO / DEFER / REQUEST CHANGES / STOP
                           ↓
         следующий независимый этап / новая задача
~~~

Принцип **Proof Before Build** остаётся обязательным: если обнаружено существующее качественное решение, лучше переиспользовать его, чем писать новое.

## 2. Подготовка задания: сначала реальный baseline

Постановщик обязан изучить **текущее** состояние всех затрагиваемых проектов, а не полагаться на отчёт предыдущего чата/агента:

- актуальные main/stable и точные SHA; открытые и объединённые PR, Issue, релизы, зависимые ветки;
- действующие AGENTS.md, проектные конституции, safety-правила и ограничения аппарата;
- код, тесты и документы, которые **уже** реализуют часть задачи;
- активную работу других агентов, ветки, locks, SHA-пины эмуляторов и контрактов;
- реальные пользовательские симптомы и критерии приёмки, включая отрицательные случаи.

Заполнить цель, scope/non-goals, инварианты, зависимости, разрешённые действия и owner GO по [AGENT-TASK-CONTRACT.md](AGENT-TASK-CONTRACT.md).

Результаты инвентаризации классифицировать: **DONE_ALREADY / CONFIRMED_GAP / HYPOTHESIS / BLOCKED / NOT_NEEDED**. Старое открытое Issue не доказывает, что реализация отсутствует.

**Стоп-фактор:** если факт или доступ неоднозначны, не создавать дубль и не трактовать UNKNOWN как разрешение на рискованное действие.

## 3. Как ставить большие ночные задания и использовать остаток лимита

Для длинной сессии составить **очередь из независимых программ**, каждая из которых сама содержит небольшие проверяемые этапы. Например: (1) надёжность роутера и восстановление, (2) безопасность серверного egress, (3) диагностика сети и лаборатория. Это пример тематического разделения, а не навсегда закреплённая очередь.

Правила:

1. Зафиксировать порядок: **сначала №1**, затем №2 и №3 только после полезного завершения, документированного STOP или безопасной передачи незакрытой части. Не считать наличие свободных токенов разрешением одновременно менять всё.
2. Программы должны иметь разные области файлов и веток. При пересечении остановить конфликтующую часть и работать над независимой.
3. **Каждый этап самодостаточен**: отрицательный тест, проверенный анализ, минимальный патч, Draft PR или обоснованное DEFER. Не открывать сразу десять незавершённых направлений.
4. По возможности сохранить результат до перехода: комментарий в существующем Issue, проверяемый commit, Draft PR и короткий handoff. Список мыслей без артефактов — не эквивалент записи в репозиторий.
5. Не сжигать оставшийся лимит ради его расходования. Исследование полезно только при конкретном вопросе и критерии STOP.
6. На две безрезультатные попытки исправить одну и ту же гипотезу — пересмотреть гипотезу, сообщить blocker и переключиться; не запускать бесконечные CI-рераны.
7. Если лимит подходит к концу, **сохранить воспроизводимые результаты** и оставить честный handoff; не ускорять merges, релизы, удаления или изменения работающих машин.
8. Большие задачи не освобождают от локальных правил отдельных проектов: производственный запуск/аппаратная приёмка/merge требуют отдельного GO.

Лучше несколько завершённых проверяемых этапов, чем один «полностью исследованный» проект, в котором нет доказательной дельты.

## 4. Исполнение каждого этапа: короткий цикл с доказательством

**Шаг A — Discovery.** Повторно открыть актуальные Issue/PR/SHA; изучить вызывающие файлы, исходную архитектуру, имеющиеся тесты. Спросить: «Уже закрыто?», «Есть ли чужой Draft PR?», «Что действительно сломано?».

**Шаг B — Evidence.** Воспроизвести проблему минимальным отрицательным тестом либо пометить SOURCE-PROVEN, HYPOTHESIS или INCONCLUSIVE с явными ограничениями. Проверить, что тест обнаружит ошибку, а не просто всегда зелёный.

**Шаг C — Minimal change.** Выбирать локальное исправление или тест; не переписывать subsystems, не улучшать косметику попутно. Новая крупная функция — только после Proof Before Build.

**Шаг D — Test.** Сначала дешёвые детерминированные тесты, потом необходимые интеграционные и QEMU/ported. Отделять mock, исходный код, реальный runtime и физическое оборудование. Логи, версии среды и точный SHA сохранять.

**Шаг E — Draft PR.** Один согласованный независимый scope на PR; указывать base/head, зависимости и проверки. Stacked PR явно помечать, не выдавать его за независимый от родительской ветки.

**Шаг F — Fresh CI.** После последнего push заново получить HEAD SHA и список GitHub Actions запусков **именно для него**. Сверить все обязательные workflows/job, их статусы и логи, а также изменение base и mergeability. Не писать «CI GREEN», если GitHub Actions показывает failure, cancelled, skipped, in_progress или проверки относятся к другому SHA; каждому исходу дать явное объяснение.

**Шаг G — Handoff.** Передать факты, ссылки, команду воспроизведения, остаточные риски и безопасный следующий шаг. Различать IMPLEMENTED, CI PASS, QEMU PASS, FIELD PASS, MERGED и PUBLISHED.

### Правила при падении CI

- Сначала прочитать **конкретный упавший job и его лог**, установить причину.
- Устаревший assertion менять только если он противоречит **подтверждённому новому контракту**; нельзя ослаблять тест просто ради PASS.
- При рассинхронизации генерируемого runtime сначала проверить source provenance и принятую процедуру сборки, а не отключать защитный gate.
- Не объяснять мультибраузерный тайм-аут «флейком» без подтверждения; увеличение тайм-аута не подменяет исправления причины.
- Различать реальную регрессию, несовместимость тестовой среды (например, локальные CRLF vs Git LF), SHA-пин другого проекта и инфраструктурную ошибку. Подтвердить отличие фактами.
- После исправления проверять **новый** commit, а не переносить предыдущий зелёный результат.

## 5. Независимое ревью и границы доверия

Рекомендуется разделять роли:

- **Постановщик/архитектор:** объясняет пользовательскую цель, границы, порядок, сохранность рабочих систем, owner GO.
- **Агент-исполнитель:** исследует, воспроизводит, изменяет отдельную ветку, тестирует, готовит Draft PR и доказательства.
- **Независимый проверяющий (человек или другой агент):** читает фактический PR и текущие CI/логи, ищет контрпримеры, конфликтующие изменения, частичные интеграции и недоказанные утверждения.
- **Владелец:** принимает решения о merge, stable, release, production и нерешённых архитектурных развилках. Отсутствие ответа не является GO.

Проверка не должна ограничиваться пересказом отчёта исполнителя. Отчёт — **навигация к доказательствам**, а не доказательство сам по себе.

Особое внимание: миграции и compatibility, жизненный цикл install/update/uninstall/watchdog/Doctor, управление чужими ресурсами, rollback, fail-closed, подписки, секреты, аппаратные ограничения.

Параллельные агенты используют отдельные ветки/worktree. Если другой агент ведёт beta/release-кандидат, не править его ветку и общие файлы без согласованной передачи владения.

## 7. Переход между разными ИИ-агентами

При смене подписки/модели НЕ переносить один огромный чат как единственный источник контекста.

Новому агенту передать:

1. Центральные нормы: [AGENTS.md](AGENTS.md), [AGENT-TASK-CONTRACT.md](AGENT-TASK-CONTRACT.md), [AGENT-ENGINEERING-STANDARD.md](AGENT-ENGINEERING-STANDARD.md), [PROOF-BEFORE-BUILD.md](PROOF-BEFORE-BUILD.md) и **этот документ**.
2. AGENTS.md целевого репозитория, его актуальные ветки/SHA, конституцию, issues, открытые и зависимые PR.
3. Одно актуальное задание из очереди, имеющиеся доказательства и **границы полномочий**.
4. Handoff: что уже проверено, что только заявлено, какие тесты не запущены, где конфликт веток, что требует владельца.
5. Критерии успеха, условия остановки и запрет самостоятельного merge/release/deploy без GO.

**Стартовый промпт для любой модели:**

~~~text
Работаешь над проектами saymer-alt. Прежде чем что-либо менять,
прочитай в saymer-alt/saymer-alt: AGENTS.md, AGENT-TASK-CONTRACT.md,
AGENT-ENGINEERING-STANDARD.md, PROOF-BEFORE-BUILD.md,
AGENT-EXECUTION-WORKFLOW.md, затем локальные AGENTS.md и safety.
Не доверяй старым сводкам: проверь живой GitHub, main/stable, PR,
тесты и фактический HEAD SHA.
Твоя цель — максимальная проверенная польза с минимальным diff.
Сначала выясни, что уже сделано; подтверждай пробел и негативный тест.
Работай в отдельной ветке, создавай только нужные Draft PR.
После push независимо сверь ВСЕ обязательные CI на окончательном SHA.
Не меняй работающие системы, main/stable, releases и релизные
каналы без отдельного owner GO. При блокере оставь доказательства
и переходи к следующему независимому разрешённому этапу.
В конце выдай матрицу DONE / BLOCKED / DEFERRED / READY FOR REVIEW
и ссылки на commit, PR, CI, воспроизведения, ограничения и риски.
Конкретное задание и актуальные refs прилагаются отдельно.
~~~

## 8. Сравнение агентов без самообмана

Пробная смена Z AI на Kimi Code или другого агента оценивается по **одинаковым заданиям сравнимой сложности**. Не делать вывод о качестве модели только по скорости ответа или проценту сожжённых токенов.

Фиксировать в кратком журнале:

| Метрика | Как проверять |
| --- | --- |
| Полезная дельта | Сколько подтверждённых дефектов/пробелов закрыто без дублирования уже сделанного |
| Качество | Сколько утверждений подтверждено реальными тестами и свежим CI; сколько обнаружено при независимом ревью |
| Эффективность | Токены/время/повторные вызовы в расчёте на **принятый результат**, если данные доступны |
| Управляемость | Соблюдение scope, STOP, отдельных веток и owner GO |
| Поддерживаемость | Минимальность diff, тесты негативного пути, понятные handoff и совместимость |
| Ограничения среды | Какие проблемы связаны с доступом, окружением, ABI, Git CRLF, CI и не доказывают дефект модели |

**Процесс сравнивать вместе с моделью.** Улучшение результата может быть вызвано качеством постановки задач, накопленными тестами и повторным использованием кода, а не обновлением модели. Не заявлять ускорение без сопоставимой базы.

## 9. Шаблон итогового handoff

~~~md
# Handoff: <задача / дата / исполнитель>
Baseline: repo, main SHA, stable SHA, head SHA
Цель и сохранённые пользовательские инварианты:
DONE_ALREADY / REUSED:
CONFIRMED_GAP / ROOT CAUSE:
Изменения: ветки, commits, Draft PR, их base и зависимости
Доказательства: команды, среда, fixtures, PASS / FAIL / UNKNOWN
Обязательные GitHub CI на ИТОГОВОМ head SHA: имя, run URL, итог
Что НЕ проверено: QEMU vs FIELD, hardware, реальные маршруты
BLOCKED / DEFERRED / NOT_NEEDED:
Возможные конфликты с параллельными PR и смежными проектами:
Что требует отдельного owner GO:
Следующая безопасная независимая задача:
~~~

**Definition of Done ночной программы:** не «всё закончено», а понятен статус каждого ограниченного этапа, все созданные изменения привязаны к доказательствам и SHA, остаточные риски не скрыты, а следующему агенту не требуется реконструировать работу по длинному чату.

---
**Короткая формула:** точное ТЗ → актуальный baseline → existing-first → воспроизведение → минимальная дельта → негативные тесты → Draft PR → свежий CI на HEAD → независимое ревью → owner GO.
