# Upstream watch — состояние, стоимость и границы (issue #16)

Дешёвый еженедельный детектор upstream-изменений для проектов saymer-alt. Заменяет четыре запланированных ChatGPT-мониторинга одним GitHub Actions workflow. **Мониторинг акций Z AI/токенов остаётся отдельной задачей и сюда не входит.**

## Статус (честно разделено)

| Статус | Значение |
|---|---|
| IMPLEMENTED | скрипт, workflow, тесты, AGENTS.md-правило, центральная issue #17 — в Draft PR |
| WORKFLOW TESTED | оффлайн-тесты 18/18 (все сценарии issue #16) + живой read-only dry-run против реального API (20 запросов, 10/10 целей) |
| SCHEDULE ACTIVE | **НЕТ** — schedule заработает только после merge PR и первого реального запуска по cron |
| OWNER REVIEW REQUIRED | merge PR; далее первый `workflow_dispatch`; далее недели 1–2 наблюдения за digest'ами |

## Компоненты

- `scripts/upstream_watch.py` — Python stdlib, без зависимостей. Конфиг 10 целей: pstack (blob `pstack/plugin.json`), NotAWDTT (HEAD main), Tachyon (latest release), OpenFlux/csqtt upstream (HEAD main, форки saymer-alt), swinter-android/ios, maxcalls (**default branch `master`**), whitelist-bypass, whitetransport-public.
- `.github/workflows/upstream-watch.yml` — cron раз в неделю (лучшее усилие, не гарантия времени) + `workflow_dispatch`; `permissions: contents: read, issues: write`; timeout 10 мин; concurrency без отмены.
- Центральная issue [saymer-alt#17](https://github.com/saymer-alt/saymer-alt/issues/17) — единственное хранилище состояния (machine-блок в теле) и место digest-комментариев.

## Почему состояние в issue и почему это надёжно

1. **Без секретов:** используется штатный `github.token`, права уже ограничены `contents: read` + `issues: write` на СВОЙ репозиторий. PAT/App/Telegram-токены не нужны и не запрашиваются.
2. **Долговечность:** issues не удаляются при перезапусках workflow, не зависят от кэшей runner'ов и живут дольше любого хранилища артефактов; тело issue редактируется атомарно API-вызовом.
3. **Прозрачность и ремонтопригодность:** состояние видно человеку в том же месте, что и digest; при порче блока парсер возвращает «нет состояния» → тихий re-baseline без лавины уведомлений (протестировано).
4. **Минимальность прав:** альтернативы хуже — коммит файла состояния требует `contents: write` (шире права, риск передвижения веток), внешний сервис требует секретов. Запись в чужие репозитории (wdtt-suite#51, KAS#236) сознательно не делается — только ссылки.

## Стоимость

- ~22–26 запросов API за прогон (2 на цель + ≤2 issue-операций), жёсткий кап 60; при исчерпании бюджета цели честно становятся `UNKNOWN`, не «тихо пропускаются».
- ~1–2 секунды CPU на runner'е раз в неделю; никакого постоянного сервера, никакой LLM. Платных API нет.
- Digest-комментарий появляется **только** при реальных новых дельтах; тело issue обновляется всегда, но правки тела уведомлений не создают.

## Контракт поведения (протестирован)

| Сценарий | Поведение |
|---|---|
| Первый запуск | baseline без digest (тихо) |
| Без изменений | без комментариев; pending-флаг дельты сохраняется |
| Одна/несколько дельт | один digest-комментарий со всеми строками (кап 10, перелив помечается) |
| Повторный запуск | без дублей (`reported` SHA не переотчётывается) |
| API error / rate limit / 404 | цель `UNKNOWN`, курсор не продвигается, workflow красный (exit 1), digest-строки нет |
| Восстановление после ошибки | первое успешное наблюдение = baseline (REVIEWED тихо), не дельта |
| Удалённый тег | `UNKNOWN not_found`, не CHANGED |
| Пересозданный тег на том же коммите | UNCHANGED; на другом — одна дельта (идентичность `tag:имя@sha`) |
| Смена default branch | `UNKNOWN` с пометкой, не CHANGED |
| Force-push туда-обратно | две честные дельты, затем тишина |
| Недоверенный текст (тег/версия вне allowlist) | не попадает в markdown вообще (цель → UNKNOWN); README/commit-сообщения не запрашиваются |
| Права | dry-run = 0 записей; с дельтами = ровно 1 комментарий + 1 PATCH тела; без дельт = 0 комментариев |

## Границы (не обещать лишнего)

- Детектор **не** проводит инженерный review: польза/лицензия/«уже реализовано» — за трекерами, агентами и Proof Before Build (правило в AGENTS.md).
- GitHub schedule неточен по времени; пропущенная неделя не создает ложных событий — сравнение всегда по сохранённому курсору.
- До merge и первого реального запуска мониторинг не считается действующим. При отказе GitHub Actions обеспечивать состояние (STOP-клауза #16) — откат к ручному агентскому ревью.
